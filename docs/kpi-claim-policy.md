# KPI ตามผู้รับเคส

- KPI รับเคส: จำนวนครั้งที่กดรับและเวลาเกิดเคสถึงรับ แยกจาก KPI แก้ไข
- KPI แก้ไข: มีรับเคสเริ่มเมื่อกดรับ; ไม่รับเคสเริ่มเมื่อเกิดเคส จบเมื่อบันทึกแก้ไขเสร็จ ไม่รวมรอตรวจยืนยัน
- ใช้ CaseActivity ACK ที่มี actorId และเวลาตรงกับเวลารับเรื่อง ไม่ใช้ adminUserId/itUserId ที่อาจถูกผู้แก้ข้อมูลล่าสุดเขียนทับ
- งานแอดมินทั้งระบบกลางและซิมต้องปิดและมีผลยืนยันหลังแก้เสร็จ โดยเวลา KPI ยังคงสิ้นสุดที่แก้เสร็จ; งานไอทีนับเมื่อบันทึกชี้แจง/สำรองเสร็จ
- การฟื้นตัวอัตโนมัติที่ไม่มีการแก้ไข และเคสพัก ไม่นับเป็นผลงานแก้เคส
- ไม่มี ACK: ต้องมี CaseActivity การแก้ไขที่ actorId ชัดเจนและเวลาแก้เสร็จตรงกัน (editedAt / after.adminUpdatedAt / after.itResolvedAt / createdAt) จึงนับให้ผู้แก้ ไม่เดาจากผู้แก้ข้อมูลล่าสุด NOTE, MASTER_UPDATED, close ไม่ใช่หลักฐานแก้สำเร็จ
- มีเวลารับแต่ไม่มีหลักฐานผู้รับ หรือมีหลักฐานผู้แก้ขัดแย้ง ไม่เดาชื่อ เก็บข้อมูลดิบและประวัติเดิมไว้
- ช่วงวันที่ในรายงานยังยึดวันตรวจพบ ส่วนเวลาตรวจพบถึงปิดเป็นสถิติวงจรเคส ไม่ใช่เวลาปฏิบัติงาน
- หน้ารายคน CSV รูปรายงาน และค่าเฉลี่ย dashboard ใช้เกณฑ์เดียวกัน

## หน้าไซต์

แยกจากงานแก้ลิงก์ ไม่ใช่โอนจำนวนเคสแอดมินไปเป็นผลงานหน้าไซต์
ต้องมีผู้ดูแลเครื่องตามช่วงเวลา ประวัติหยุดส่งผลตรวจ/ออฟไลน์ และช่วงเคสรอตรวจยืนยันที่ทับซ้อนกัน
lastSeenAt เป็นเพียงสถานะล่าสุดและไม่พิสูจน์สาเหตุปิดเคสช้า ห้ามนำเวลารอทั้งหมดไปลงโทษพนักงาน
ผู้ใช้ยืนยันผู้ดูแลวันที่ 25 กันยายน 2026:

| เครื่องตรวจ | ผู้ดูแล |
| --- | --- |
| True | ไอติม |
| AIS | ไอติม |
| Dtac | อุ้ม |

ผูกผู้ดูแลบน production แล้ว; รายละเอียด KPI ขาดการติดต่อใน offline-kpi.md
ผูกด้วยรหัสเครื่อง ไม่ผูกอัตโนมัติจากค่ายซิมที่รายงาน เพราะเปลี่ยนซิมได้และไม่ได้หมายถึงเปลี่ยนผู้ดูแล
เริ่มเก็บประวัติใหม่เมื่อเปิดใช้จริง ไม่ย้อนหลังช่วงการมอบหมายหรือสร้างข้อมูลออฟไลน์ขึ้นเอง

เปลี่ยนสูตรรายงาน ไม่เขียนทับประวัติเคสเดิมหรือเปลี่ยนสิทธิ์บัญชี
