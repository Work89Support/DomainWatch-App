# KPI ตามผู้รับเคส

- งานแอดมินและไอทีเริ่มเมื่อกดรับเคส จบเมื่อบันทึกแก้ไขเสร็จ ไม่รวมช่วงก่อนรับและรอตรวจยืนยัน
- ใช้ CaseActivity ACK ที่มี actorId และเวลาตรงกับเวลารับเรื่อง ไม่ใช้ adminUserId/itUserId ที่อาจถูกผู้แก้ข้อมูลล่าสุดเขียนทับ
- เคสซิมต้องปิดและมีผลยืนยันหลังแก้เสร็จ จึงนับผลงานให้ผู้รับเคส โดยเวลา KPI ยังคงสิ้นสุดที่แก้เสร็จ
- การฟื้นตัวอัตโนมัติที่ไม่มีการแก้ไข และเคสพัก ไม่นับเป็นผลงานแก้เคส
- ข้อมูลเก่าที่ไม่มีหลักฐาน ACK ไม่เดาชื่อจากผู้แก้ล่าสุดหรือชื่อแสดงผล เก็บข้อมูลดิบและประวัติเดิมไว้
- ช่วงวันที่ในรายงานยังยึดวันตรวจพบ ส่วนเวลาตรวจพบถึงปิดเป็นสถิติวงจรเคส ไม่ใช่เวลาปฏิบัติงาน
- หน้ารายคน CSV รูปรายงาน และค่าเฉลี่ย dashboard ใช้เกณฑ์เดียวกัน

## หน้าไซต์ (ยังไม่เปิดการคำนวณ)

แยกจากงานแก้ลิงก์ ไม่ใช่โอนจำนวนเคสแอดมินไปเป็นผลงานหน้าไซต์
ต้องมีผู้ดูแลเครื่องตามช่วงเวลา ประวัติหยุดส่งผลตรวจ/ออฟไลน์ และช่วงเคสรอตรวจยืนยันที่ทับซ้อนกัน
lastSeenAt เป็นเพียงสถานะล่าสุดและไม่พิสูจน์สาเหตุปิดเคสช้า ห้ามนำเวลารอทั้งหมดไปลงโทษพนักงาน
ผู้ใช้ยืนยันผู้ดูแลวันที่ 25 กันยายน 2026:

| เครื่องตรวจ | ผู้ดูแล |
| --- | --- |
| True | ไอติม |
| AIS | ไอติม |
| Dtac | อุ้ม |

นี่คือการมอบหมายที่ยืนยันแล้ว ยังไม่ใช่การบันทึกลงฐานข้อมูล production
ก่อนบันทึกจริงต้องตรวจสอบรหัสเครื่องและรหัสบัญชีพนักงานที่ตรงกัน (ชื่อในภาพ: มือถือ-ไอติม และ มือถือ-อุ้ม)
ผูกด้วยรหัสเครื่อง ไม่ผูกอัตโนมัติจากค่ายซิมที่รายงาน เพราะเปลี่ยนซิมได้และไม่ได้หมายถึงเปลี่ยนผู้ดูแล
เริ่มเก็บประวัติใหม่เมื่อเปิดใช้จริง ไม่ย้อนหลังช่วงการมอบหมายหรือสร้างข้อมูลออฟไลน์ขึ้นเอง

การแก้ครั้งนี้ไม่มีการย้ายฐานข้อมูล ลบประวัติ เปลี่ยนสิทธิ์บัญชี หรือ deploy
